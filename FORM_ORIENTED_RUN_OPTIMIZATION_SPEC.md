# Устаревшая редакция: техническая спецификация прогонов по основной форме

> Целевая модель описана в `BRAND_ORIENTED_RUN_OPTIMIZATION_SPEC.md`. Этот файл сохранён для сравнения со старой реализацией.

## 1. Назначение

Документ описывает реализацию модели, в которой автотесты разделены по основной форме, а не по бренду. Каждая Jenkins job полноценно проверяет одну форму на общем активном наборе URL всех брендов и выполняет presence-check остальных ожидаемых форм.

Спецификация является техническим основанием для реализации и приемки. Она не меняет бизнес-правила конкретных лендингов: ожидаемые формы, success-маркеры и исключения должны браться из текущего кода и конфигурации проекта.

## 2. Цели

- Уменьшить длительность отдельного form-job.
- Обнаруживать проблему конкретного лендинга в текущем form-job, не ожидая прогона другого бренда.
- Исключить перенос popup, введенных данных, cookies и локаторов между URL.
- Сохранить полную проверку каждой активной формы один раз за полный цикл.
- Проверять наличие остальных ожидаемых форм без повторной отправки заявок.
- Продолжать обработку URL после ошибки на одном лендинге.

## 3. Не входит в задачу

- Изменение бизнес-логики форм и success-маркеров без отдельного решения.
- Параллельный запуск URL.
- Автоматическое включение отключенных business-сценариев.
- Удаление старого режима до завершения сравнительного прогона.
- Изменение текущего расписания сводных уведомлений.

## 4. Термины

| Термин | Определение |
| --- | --- |
| `form_job` | Jenkins job, у которой одна форма является основной для полного функционального сценария. |
| `primary_form` | Форма, которую текущий job заполняет и отправляет. |
| `presence_check` | Проверка наличия и открываемости ожидаемой формы без заполнения и submit. |
| `full_functional_check` | Полный сценарий формы: popup, поля, submit и подтверждение результата. |
| `url_case` | Изолированный набор проверок одного URL в рамках одного form-job. |
| `form_cycle` | Последовательный запуск всех согласованных form-job. |

## 5. Целевая архитектура

### 5.1. Набор form-job

Базовая цепочка:

```text
profit -> connection -> checkaddress -> undecided -> profit
```

Рекомендуемый набор активных job:

```text
FORM_JOB_PROFIT
FORM_JOB_CONNECTION
FORM_JOB_CHECKADDRESS
FORM_JOB_UNDECIDED
```

`connection_cards`, `moving` и `express` включаются как отдельные form-job только после проверки, что у них действительно отдельный триггер, набор полей или success-поведение. `business` в цепочку не включается, пока бизнес-шаги отключены.

### 5.2. Граница одного job

Входом job является фиксированный `PRIMARY_FORM`. Разбиение по брендам не используется как основной уровень запуска.

Каждый job:

1. загружает активные URL всех брендов;
2. отбирает URL, для которых конфигурация ожидает `PRIMARY_FORM`;
3. выполняет URL последовательно, по одному;
4. записывает независимый результат каждого URL;
5. завершает job только после обработки всего набора.

## 6. Контракт запуска

### 6.1. Обязательные параметры

| Параметр | Значение | Назначение |
| --- | --- | --- |
| `PRIMARY_FORM` | `profit`, `connection`, `checkaddress`, `undecided` | Форма полного сценария текущего job. |
| `URL_SCOPE` | `all-active` | Использовать все активные URL всех брендов. |
| `RUN_MODE` | `form-oriented` | Явно выбрать новый режим, не смешивая его со старым `all`. |
| `PROXY_CREDENTIAL_ID` | Jenkins credential id | Использовать текущий секрет прокси без хранения значения в коде. |

Дополнительные параметры браузера, окружения, уведомлений и Allure сохраняются из текущего Jenkins-контракта.

### 6.2. Инварианты запуска

- В активном form-oriented job нельзя передавать `PRIMARY_FORM=all`.
- Значение `PRIMARY_FORM` должно быть валидировано до начала обработки URL.
- Неизвестная форма должна завершать job конфигурационной ошибкой до открытия сайтов.
- Секреты не выводятся в Jenkins log, Allure, Telegram или артефакты.

## 7. Формирование URL-скоупа

Требуется общий агрегатор URL поверх существующих файлов брендов и текущих allowlist-правил.

Агрегатор должен:

1. загрузить URL из всех активных файлов брендов;
2. исключить закомментированные строки и отключенные URL;
3. сохранить метаданные `brand`, исходный URL и ожидаемые формы;
4. нормализовать URL для дедупликации, не меняя URL, используемый браузером без отдельного правила;
5. убрать дубликаты, сохранив список брендов, которым принадлежит URL;
6. отфильтровать URL по `PRIMARY_FORM`;
7. вернуть стабильный порядок URL для воспроизводимых прогонов.

Текущая загрузка URL, рассчитанная на один бренд за запуск, должна быть переиспользована внутри агрегатора, а не продублирована в Jenkinsfile.

Если URL содержит несколько ожидаемых форм, он попадает в несколько form-job, но полноценно проверяется только в job соответствующей основной формы.

## 8. Обработка одного URL

Для каждого `url_case` используется следующий порядок:

1. Создать новый browser context или эквивалентное чистое состояние.
2. Открыть URL и дождаться согласованного состояния страницы.
3. Выполнить presence-check всех ожидаемых форм URL.
4. Для `PRIMARY_FORM` выполнить full functional check.
5. Записать результат с привязкой к URL, бренду, форме и типу проверки.
6. Закрыть page/context независимо от результата.
7. Перейти к следующему URL.

После каждого URL запрещено переиспользовать:

- page и popup handles;
- локаторы, полученные на предыдущей странице;
- введенные значения;
- cookies и storage, если они не являются явно обязательной частью окружения;
- URL подтверждения `thanks`;
- флаги состояния предыдущего сценария.

Ошибка открытия, timeout, ошибка popup, ошибка заполнения или ошибка submit должна локализоваться на текущем `url_case` и не останавливать следующий URL.

## 9. Presence-check

Presence-check проверяет остальные формы и не создает заявку.

Минимальный контракт проверки:

1. Найден ожидаемый триггер формы.
2. Триггер видим и доступен для взаимодействия.
3. Popup открывается либо форма доступна в согласованном inline-виде.
4. В открытом состоянии найден идентификатор формы и обязательные поля.
5. Popup закрывается, либо состояние страницы сбрасывается.

Presence-check не должен:

- заполнять пользовательские данные;
- нажимать submit;
- ждать success URL;
- использовать успех другой формы как собственный успех.

Результат маркируется `check_kind=presence`.

## 10. Full functional check

Для `PRIMARY_FORM` используется существующая бизнес-логика соответствующего сценария с адаптацией к form-oriented режиму.

Обязательные этапы:

1. открыть нужный popup или inline-форму;
2. заполнить обязательные поля текущими тестовыми данными;
3. выполнить submit;
4. подтвердить успех согласованным success-маркером;
5. записать результат.

Успешный submit считается успехом только при выполнении текущего правила подтверждения проекта. Если существующий сценарий допускает несколько success-маркеров, они должны быть перечислены в конфигурации и отражены в тесте.

Результат маркируется `check_kind=full` и содержит `primary_form`.

## 11. Изоляция ошибок и статус job

Обработчик URL должен использовать эквивалент следующей семантики:

```text
for url_case in url_scope:
    try:
        run_presence_checks(url_case)
        run_primary_form(url_case)
    except Exception as error:
        record_url_failure(url_case, error)
    finally:
        close_context()
```

Правила:

- одна ошибка не прерывает список URL;
- все URL должны получить финальный статус, включая `skipped` с причиной;
- после завершения набора job получает failure, если был хотя бы один функциональный или presence-дефект;
- failure финального статуса не отменяет публикацию Allure и итогового отчета;
- инфраструктурная ошибка до формирования URL-скоупа может остановить job как конфигурационная ошибка.

## 12. Jenkins-цепочка

Каждый downstream build получает `PRIMARY_FORM` явно. Состояние текущей формы не хранится только в workspace или в локальном файле.

Требования:

- job запускает только один `PRIMARY_FORM`;
- следующий job запускается после завершения текущего, согласно текущей политике Jenkins;
- после `undecided` цепочка возвращается к `profit`;
- перезапуск отдельного job не должен незаметно менять форму следующего запуска;
- переход между job должен быть виден в Jenkins build parameters и логах;
- при необходимости оставляется feature flag для старого brand-oriented режима на период миграции.

## 13. Отчетность

Каждый результат должен содержать следующие атрибуты:

```text
brand
url
primary_form
check_kind: full | presence
step
status
error_type
error_detail
```

Allure должен позволять отфильтровать:

- все ошибки конкретного URL;
- ошибки конкретного бренда;
- full-check выбранной формы;
- presence-check;
- ошибки текущего form-job.

Telegram-уведомление form-job должно указывать:

- имя job и номер build;
- `primary_form`;
- количество обработанных URL;
- количество full и presence проверок;
- количество успешных и ошибочных URL;
- список ошибок с брендом, URL, типом проверки, шагом и деталями.

Сводные отчеты по расписанию сохраняются отдельно и не должны превращать каждый presence-check в отдельный независимый спам-алерт.

## 14. Критерии приемки

### AC-01. Скоуп

- При запуске `PRIMARY_FORM=profit` обрабатываются все активные URL всех брендов, для которых ожидается `profit`.
- Закомментированные и отключенные URL не обрабатываются.
- Дубликаты не создают повторный `url_case` в одном form-job.

### AC-02. Полная и presence-проверка

- На каждом URL выбранная основная форма проходит full-check.
- Остальные ожидаемые формы проходят только presence-check.
- Presence-check не выполняет submit.

### AC-03. Изоляция

- Новый URL получает чистое состояние page/context.
- Ошибка и popup предыдущего URL не влияют на следующий URL.
- После timeout следующий URL запускается штатно.

### AC-04. Продолжение прогона

- Ошибка одного URL не останавливает обработку оставшихся URL.
- В итоговом отчете присутствует ошибка исходного URL.
- Финальный статус job отражает наличие ошибки после завершения всего скоупа.

### AC-05. Цикл

- Цепочка передает правильный `PRIMARY_FORM` в каждый job.
- Полный цикл включает все согласованные формы ровно по одному разу.
- После последней формы начинается следующий цикл с первой формы.

### AC-06. Диагностика

- Allure различает `full` и `presence`.
- Ошибку можно связать с брендом, URL, основной формой и шагом.
- Уведомление не содержит секретов и дает ссылку на Jenkins/Allure по текущему контракту проекта.

### AC-07. Производительность

- Сравнение выполнено на сопоставимом URL-скоупе.
- Зафиксированы wall-clock time, количество открытий URL, full-check и submit.
- Результат сравнения не ухудшает полноту проверки форм за полный цикл.

## 15. План тестирования

### Unit

- агрегация URL всех брендов;
- фильтрация комментариев и отключенных URL;
- дедупликация с сохранением brand metadata;
- фильтрация по `PRIMARY_FORM`;
- валидация неизвестной формы;
- формирование стабильного порядка URL.

### Интеграционные проверки

- URL с одной формой;
- URL с несколькими формами;
- отсутствующий триггер;
- popup, который не открылся;
- открывшийся popup без обязательного поля;
- успешный submit;
- timeout при открытии или submit;
- ошибка на первом URL и успешный следующий URL;
- переход на `thanks` и корректное начало следующего URL.

### Jenkins / отчетность

- запуск каждого form-job с правильным параметром;
- переход всей цепочки;
- повторный запуск отдельной формы;
- публикация Allure при наличии ошибок;
- итоговое уведомление после полного URL-скоупа;
- отсутствие секретов в логах и сообщениях.

## 16. План внедрения

1. Добавить feature flag `RUN_MODE=form-oriented` без удаления старого режима.
2. Реализовать агрегатор URL и unit-тесты его правил.
3. Перенести один form-job, предпочтительно `profit`, на малом сопоставимом скоупе.
4. Сравнить результаты, полноту и длительность со старым режимом.
5. Подключить остальные согласованные формы и цепочку.
6. После успешного полного цикла принять решение об отключении старого режима.

## 17. Открытые решения до реализации

1. Финальный перечень form-job: входят ли `connection_cards`, `moving` и `express` как отдельные job.
2. Точное правило, какие формы ожидаются на каждом URL.
3. Нужны ли URL-шарды после измерения длительности общего form-job.
4. Остаются ли отдельные build-уведомления вместе со сводными уведомлениями.
5. Какой набор success-маркеров является нормативным для каждой формы.
