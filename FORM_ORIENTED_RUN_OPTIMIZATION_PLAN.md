# План оптимизации прогонов по формам

## 1. Цель

Сократить длительность автотестов и ускорить обнаружение проблем на отдельных лендингах без смешивания состояний разных форм и без снижения контроля наличия ожидаемых форм.

## 2. Текущая проблема

Сейчас запуск организован вокруг брендов и нескольких form-suite. Один и тот же URL может проходить несколько полноценных сценариев в рамках одного большого прогона:

- открытие страницы;
- поиск и открытие popup;
- заполнение формы;
- отправка заявки;
- ожидание подтверждающего URL;
- возврат на страницу.

Из-за этого один URL посещается повторно для разных типов форм, а полный прогон занимает значительное время.

## 3. Предлагаемая модель

Главным уровнем разделения становятся формы, а не бренды.

Для каждой основной формы создается отдельная Jenkins job:

```text
profit
connection
checkaddress
undecided
```

Список форм должен быть согласован с фактически активными сценариями. Отдельные варианты, например `connection_cards`, рассматриваются как самостоятельный сценарий только если отличаются по триггеру или поведению.

`business` не включается в рабочую цепочку, пока бизнес-шаги отключены.

## 4. Логика одной form-job

Каждая job проходит все активные URL всех брендов, где для URL ожидается выбранная основная форма.

Для каждого URL выполняется последовательность:

1. Открыть URL.
2. Найти и проверить наличие всех ожидаемых форм.
3. Для основной формы выполнить полный сценарий:
   - открыть нужный popup;
   - заполнить поля;
   - отправить заявку;
   - проверить подтверждение (`thanks`, `submitted` или другой согласованный success URL);
   - корректно завершить сценарий.
4. Закрыть страницу или контекст.
5. Перейти к следующему URL.

Остальные формы не заполняются и не отправляются. Для них выполняется только presence-проверка.

## 5. Presence-проверка

Presence-проверка не должна ограничиваться наличием CSS-класса в DOM.

Минимальная проверка формы:

- найден ожидаемый триггер;
- триггер доступен для взаимодействия;
- popup открывается;
- внутри popup найдены признаки нужной формы и обязательные поля;
- popup корректно закрывается или страница возвращается в исходное состояние.

Если ожидаемая форма отсутствует, это считается ошибкой на текущем URL независимо от того, какая форма является основной в текущей job.

## 6. Изоляция URL

URL проверяются последовательно, по одному.

Для каждого URL используется чистое состояние страницы. Нельзя переносить между URL:

- открытые popup;
- введенные значения;
- cookies и состояние формы;
- текущий URL `thanks`;
- локаторы или ссылки на элементы предыдущей страницы.

Ошибка одного URL не должна останавливать обработку остальных URL. Она фиксируется в Allure, после чего job продолжает прогон.

## 7. Цепочка form-job

Формы запускаются последовательно отдельными job:

```text
profit -> connection -> checkaddress -> undecided -> profit
```

Один полный цикл заканчивается после прохождения всех выбранных form-job.

Таким образом:

- каждая форма полноценно проверяется один раз за цикл;
- все остальные формы проверяются на наличие на каждом URL;
- после завершения цикла начинается следующий цикл с первой формы.

## 8. Отчетность и уведомления

Каждая form-job формирует отдельный:

- Allure-отчет;
- Telegram-отчет по своему билду;
- список успешных и ошибочных URL;
- информацию о том, какая форма была основной.

В отчете нужно разделять:

- `full functional check` — полноценный сценарий основной формы;
- `presence check` — проверка наличия остальных ожидаемых форм.

Для ошибки на конкретном лендинге должно быть видно:

- бренд;
- URL;
- основная форма текущего прогона;
- тип ошибки: функциональная или presence;
- шаг и детали.

## 9. Ожидаемый эффект

При текущей структуре один большой прогон многократно запускает полноценные form-сценарии на одних и тех же URL.

Новая модель должна:

- сократить количество дорогих submit-сценариев внутри одного билда;
- уменьшить длительность отдельной job примерно в 2–3 раза;
- снизить нагрузку на сайты и прокси;
- быстрее показывать проблему конкретного лендинга;
- упростить повторный запуск только проблемной формы;
- сохранить полную функциональную проверку всех форм за цикл.

Точная экономия времени подтверждается сравнительным прогоном на одинаковом наборе URL.

## 10. Риски и ограничения

### Риск: presence-проверка даст ложный успех

Меры:

- проверять открытие popup, а не только DOM-селектор;
- проверять обязательные поля формы;
- использовать отдельное состояние для каждого popup.

### Риск: ошибка остановит весь form-job

Меры:

- изолировать результат каждого URL;
- продолжать обработку после падения отдельного тест-кейса;
- отправлять итоговый отчет после завершения всех URL.

### Риск: одна form-job станет слишком длинной

Меры:

- сохранять URL-шарды;
- при необходимости делить job по URL-шардам, а не по брендам;
- не включать параллельность до проверки влияния на rate limit и прокси.

### Риск: полноценная проверка формы будет происходить реже

Это осознанный компромисс модели. Каждая форма полноценно проверяется один раз за полный цикл, а наличие всех остальных форм проверяется на каждом URL каждого form-job.

## 11. Критерии готовности

Решение можно считать готовым, если:

- form-job проходит все активные URL всех брендов выбранной формы;
- один URL не смешивает состояние с предыдущим URL;
- основная форма проходит полный submit-сценарий;
- остальные ожидаемые формы проверяются на наличие;
- падение одного URL не останавливает остальные URL;
- Allure различает full и presence проверки;
- Telegram показывает form-job и конкретный URL;
- полный цикл включает все согласованные формы;
- сравнение с текущим запуском подтверждает сокращение времени.
